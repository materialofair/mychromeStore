# 上传、审核与账号管理

发布中心位于 `/publish.html`，首页侧栏提供入口。它提供多扩展目录、ZIP 上传、逐版本审核和公开下载。现有首页的 **Focus Notes Demo 目录更新面板**继续独立使用；已发布扩展可进入独立的「安装与更新」页面（`/update.html?id=扩展ID`）。首次手动加载后，绑定同一目录即可更新。目录、备份与锁按扩展 ID 隔离；支持商店桥接的扩展可自动请求重载，否则提示手动重载。

## 启动和首次建号

需要 Node.js 22.13 或更高版本（推荐 Node 24 LTS）。运行：

```sh
npm ci
npm run admin:create
npm run dev
```

`admin:create` 在本地终端交互创建第一个管理员，密码隐藏输入，不预置任何账号密码。仅空数据库允许初始化。不要把密码写进 shell 命令、Git 仓库或聊天记录。然后访问 `http://localhost:5173/publish.html` 登录。

开发模式同时启动 Vite（5173）和后端（8787），浏览器所有 API 都通过 Vite 同源代理访问。不要混用 localhost 与 127.0.0.1：Origin 必须与后端配置一致。

## 谁能做什么

| 角色 | 能力 |
|---|---|
| 访客 / 普通用户 viewer | 浏览、下载已批准的扩展 |
| 开发者 developer | 上传自己的扩展，查看自己的提交与审核结果 |
| 审核员 reviewer | 查看提交、下载待审包、批准或驳回 |
| 管理员 admin | 创建和管理账号、上传、审核他人提交、下架版本 |

管理员在「账号管理」中创建账号并指定角色；没有自助注册。密码 12–128 字符。更改角色、禁用或重设密码会使该账号已有登录失效，至少保留一个有效管理员。管理员自己上传的包也必须由另一名审核员或管理员批准。

## 开发者怎样准备和上传

1. 把扩展文件放在 ZIP 根目录，根目录应包含 `manifest.json`，不能多套一层文件夹。
2. Manifest 使用 V3；直接填写 `name`（不使用 `__MSG_...__` 本地化名称），版本使用 `1.0.0` 这样的三段数字，每段 0–65535，不能全部为 0。
3. 为 Manifest 设置固定 `key`，即至少 2048 位 RSA 公钥的 DER/SPKI Base64 表示。它用于稳定浏览器扩展 ID；**不要上传私钥**。后续版本维持相同的公钥。
4. 登录开发者账号，选择 ZIP 并提交。服务器验证后进入待审核；提交记录中可以查看原因和状态。
5. 新版本再次上传完整 ZIP。版本不可覆盖，即使被驳回或下架，也要增加版本号重新提交。首次提交将该扩展 ID 归属给当前开发者，其他开发者不能上传同 ID。

包限制：ZIP 最大 32 MiB，单文件解压最大 24 MiB，总解压最大 64 MiB，最多 512 个文件（目录与文件合计不超过 1024 个条目）。文件名仅支持英文字母、数字、下划线、连字符及普通扩展名；不接受隐藏文件、Windows 保留名、大小写重名、软链接、加密包、ZIP64 或路径穿越。建议打包前移除 `.DS_Store`、`__MACOSX` 等系统辅助文件。

`key` 是公开身份标识，并不能证明开发者拥有该扩展的签名私钥。因此只应给受信任的人分配上传权限，并在首次审核时核实扩展作者。内置 Focus Notes Demo ID 已保留，不能通过发布中心占用。

### 为自己的扩展生成固定身份

如果扩展尚无 `manifest.key`，运行：

```sh
npm run extension:key
```

将输出的 `key` 字符串复制到 `manifest.json` 的顶层 `key` 字段，记录对应的 `extensionId`。每个扩展只生成一次，后续版本沿用同一个 key。脚本仅输出公钥，不保存或输出私钥，也不用于 CRX 签名。已有固定身份的扩展应沿用原公钥；给已安装扩展改 key 会改变其 ID，应先备份本地数据。

### 体验上传审核

```sh
npm run example
```

会在 `.data/examples/` 生成两个独立的 **Hello SPACE** ZIP（1.0.0 与 1.1.0），可以用开发者账号依次上传。该脚本生成独立公钥并在本地保存，后续执行复用公钥，私钥不写盘。不要上传内置 Focus Notes 包，它的 ID 已保留。

## 审核和公开

审核员打开提交详情，可比较权限变化、查看文件列表及 SHA-256，并下载源包进行人工检查。包不会在网站内执行或渲染。

批准后，版本才出现在公开目录和下载接口中。新版本仍在待审时，已有批准版本继续可用。比现有已批准版本更低的版本不能被批准。驳回必须填写原因；开发者修正后升版再提交。

管理员可以填写原因下架某个已批准版本。下架后，其公开 JSON 和 ZIP 直链都返回 404，目录回到仍获批准的最高版本；如果没有其他批准版，该扩展不在公开目录展示。已经下载到用户设备上的文件无法撤回。

系统记录上传人、审核人、时间、原因和审计事件。自动校验用于包结构和一致性验证，**不等于恶意代码检测**；审批前仍需人工检查源码、权限和行为。

## 生产部署

这是包含后端的部署，发布功能不能只托管 `dist/` 静态目录。示例：

```sh
STORE_ORIGIN=https://extensions.example.com npm run build
TRUST_PROXY=1 STORE_ORIGIN=https://extensions.example.com npm start
```

通过 HTTPS 反向代理将站点请求转发到本机后端 8787；参考 `deploy/nginx.conf`。`STORE_ORIGIN` 为准确的 HTTPS 来源，不包含路径或末尾斜杠。线上登录 Cookie 带 Secure 标记，生产浏览器必须通过 HTTPS 访问；仅 localhost 开发允许 HTTP。后端默认仅监听回环地址。示例 Nginx 会覆盖 `X-Real-IP`；后端仅在显式设置 `TRUST_PROXY=1` 且连接来自回环地址时采用该头部做登录限流。直连开发环境保持默认关闭，不信任外部转发头。

数据在 `.data/store.sqlite`，包含用户密码哈希、会话、扩展包和审核记录，已加入 Git 忽略。不要把 `.data` 放在任何静态服务器根目录或公开存储桶中；数据库及备份应限制为服务账号可读写。备份请先停止服务再复制整个数据目录，恢复时保持服务器关闭，确保备份不会上传到代码仓库。上线前先完成账号配置、HTTPS 和数据备份。

当前默认最多 1000 个账号；每个开发者最多 10 个待审版本、512 MiB 持久化包与版本 JSON，全站最多 4 GiB。被驳回或下架的包仍保留用于审计并计入配额；当前没有删除历史包的界面，达到配额后需运维规划归档或扩容。可用 `MAX_USER_STORAGE_MIB`、`MAX_TOTAL_STORAGE_MIB`、`MAX_PENDING_UPLOADS` 调整配额。默认同时处理 1 个上传，`MAX_CONCURRENT_UPLOADS` 可设 1–4；提高前应评估内存。会话有效期 8 小时；同一账号新登录会使此前登录失效。

SQLite 方案适合单机内部使用，不支持多副本应用共享本地数据库。首次管理员忘记密码且无其他管理员时，需要运维在受控环境处理账号恢复；当前没有邮箱找回或公开密码重置入口。

## 技术参考

- [Node.js SQLite API](https://nodejs.org/download/release/v22.13.1/docs/api/sqlite.html)：本项目使用内置 SQLite，本地单进程运行。
- [fflate](https://github.com/101arrowz/fflate)：生成 ZIP；上传解压另行使用严格 ZIP 结构验证与限制输出的 Node zlib，不仅信任包内声明的大小。

## browsa 适配包

运行 `npm run browsa:build` 生成完整 SPACE AI ZIP，再按开发者上传、独立审核流程发布。构建与自定义模型配置见 [适配指南](../extensions/space-browsa/README.md)。更新需要当前本地版本仍有已批准的发布记录；旧版下架时停止更新并提示手动安装，不公开下架包。本地备份的身份核验不依赖公开版本列表，因此下架后仍可恢复。
